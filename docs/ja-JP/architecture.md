# 構造と背景

**言語** · [English](../en/architecture.md) · [한국어](../ko-KR/architecture.md) · 日本語 · [← README](README.md)

`speexrelay` が何をするプログラムで、なぜこの形になったのかを書き残します。
後から手を入れるとき、同じ場所を掘り返さないためのものです。

作業日 2026-09-12。

---

## 1. なぜエコーが起きるのか

通話中、相手の声がスピーカーから出ます。その音が空気を伝ってこちらのマイクに
再び入ります。マイクに入ったものは通話回線を通って相手に戻るので、相手は自分が
話した言葉を数百ミリ秒後にもう一度聞くことになります。これがエコーです。

**聞こえているのは相手であって、こちらではありません。** 自分の耳で問題を確認
できないので、通話のたびに相手に尋ねるしかありません。この作業に時間がかかった
理由の一つがこれです。

解決方向は二つです。

**スピーカーの音がマイクに入らないようにする。** ヘッドセットを使えば解決します。
ただしスピーカーで通話したい場合には使えません。

**マイクに入ったエコーを消す。** これが AEC(音響エコーキャンセル)です。
スピーカーへ送った信号は分かっているのだから、マイク信号からそれを引けばよい、
という発想です。このリポジトリはこちらです。

### なぜ単純な引き算ではないのか

スピーカーへ送った信号と、マイクに戻ってきた信号は同じではありません。部屋を
一周する間にこう変わります。

- **遅延。** スピーカーからマイクまでの伝搬時間に、オーディオデバイスがバッファに
  溜める時間が加わります。ここでの実測値は 115 ms でした。
- **減衰と歪み。** スピーカーとマイクの周波数特性が異なり、壁の反射音が重なります。
- **残響。** 一度の音が複数の経路で反射し、時間をかけて到着します。

そのため AEC は「スピーカー信号がマイクに届くときどんな形になるか」をリアルタイム
に推定します。この推定を**適応フィルタ**と呼び、推定したものをマイク信号から引く
のがエコーキャンセルです。通話の間ずっと学習を続けます。

## 2. macOS はなぜやってくれないのか

FaceTime と電話アプリは `avconferenced` というシステムデーモンがオーディオを
処理します。この中に AEC はあるのですが、この構成では働きませんでした。

Apple が開発者に提供する AEC は `AUVoiceProcessingIO`(VPIO)というオーディオ
ユニットです。三通り試し、三つとも塞がれました。

| 試したこと | 結果 |
|---|---|
| VPIO にマイクだけ繋ぎ、システム出力を参照に使う | 参照コールバックが一度も呼ばれない(`cb=0`) |
| VPIO の出力で相手の声をレンダリングし、その信号を参照に使う | マイクから仮想デバイスへの経路が死ぬ |
| Aggregate Device でマイクとスピーカーを一つにまとめる | `-10851` エラーで拒否 |

**一つ目の失敗が核心です。** VPIO のキャンセラーは**自分自身の出力バスへ
レンダリングされた信号だけ**を参照に使います。`avconferenced` がスピーカーへ直接
送った音は VPIO からは見えないので、参照が存在しません。参照のない AEC は何も
消せません。

三つ目も同じ制約から来ています。`kAudioOutputUnitProperty_CurrentDevice` は
デバイスを一つしか受け取りません。入力はマイク、出力はモニタと別々に繋ぐには
Aggregate Device が必要ですが、VPIO がそれを拒否します。

もう一つ、Core Audio の **process tap** も試しました。他プロセスのオーディオ出力
を横取りする API ですが、tap の生成までは成功しコールバックが一度も来ませんでした。
署名のない CLI バイナリにはシステムオーディオ録音の権限(TCC)がないためと見られ
ます。

**結論はこうです。** Apple のキャンセラーは参照信号を受け取れないので使えず、
システムオーディオを直接横取りするのも権限で塞がれています。参照信号も AEC
エンジンも別の手段で用意するしかありません。

## 3. BlackHole が必要な理由

参照信号を得るには、相手の声がスピーカーへ行く**前**にその信号を見る必要が
あります。`avconferenced` がスピーカーへ直接送ってしまうと、見る方法がありません。

そこで通話アプリの出力を**仮想オーディオデバイス**へ回します。仮想デバイスは出力
として使うと音を飲み込み、入力として使うと飲み込んだその音をそのまま返します。
通話アプリがそちらへ音を送れば、こちらのプログラムから読めます。

`BlackHole` がその仮想デバイスです。オープンソースで、Homebrew で入ります。

二組必要です。一つは相手の声を受け取る通り道(通話アプリ → 中継)、もう一つは
処理したマイク信号を送る通り道(中継 → 通話アプリ)。向きが逆なので同じデバイス
は使えません。

Homebrew には `blackhole-2ch`、`blackhole-16ch`、`blackhole-64ch` が別々にあり、
2ch を二つ入れる方法がありません。そこで 2ch と 16ch を一つずつ入れています。
**16 チャンネルが必要だから選んだのではなく、別々のデバイスが必要だから選んだ**
ということです。

この選択が後で問題を一つ生みました。6 節で扱います。

## 4. 信号の流れ

デバイスが四つ関わります。

```
                     相手の声
                        |
              [FaceTime / 電話アプリ]
                    |        ^
         出力       |        |     マイク
                    v        |
          BlackHole 16ch   BlackHole 2ch
                    |        ^
                    |        |
        +-----------+--------+-----------+
        |         speexrelay             |
        |                                |
        |   参照信号 ---> [speexdsp AEC]  |
        |       |              ^         |
        |       v              |         |
        |   [スピーカー]   マイク信号      |
        +-----------|----------|---------+
                    |          |
                    v          |
                スピーカー    マイク
                    |          ^
                    +--エコー--+
                    (空気を伝って)
```

経路ごとに追うとこうなります。

**相手の声が来る道。** FaceTime が BlackHole 16ch へ出力します。中継がそれを読み、
二箇所へ送ります。一つは実際のスピーカー(利用者が聞く)、もう一つは AEC の参照
入力です。**同じ信号を二つの役割に分けるのがこの構造の核心です。**

**こちらの声が行く道。** マイクから読んだ信号を AEC に入れます。AEC が参照を使って
エコー成分を引き、結果を BlackHole 2ch へ書きます。FaceTime はそれをマイク入力と
して受け取ります。

**エコーができる道。** スピーカーから出た音が空気を伝ってマイクに入ります。これが
消すべき対象で、参照信号と同じ原本から来ているので消せます。

`speexrelay` が動いていないと、BlackHole 16ch に入った音を誰も取り出しません。
相手の声がそこで消えます。**中継を先に立ち上げてから通話しなければならない理由が
これです。**

## 5. コード構造

`speexrelay.swift` の一ファイルです。

### 四つのオーディオコールバック

CoreAudio はリアルタイムスレッドでコールバックを呼びます。この中で時間のかかる
処理をすると音が途切れるので、コールバックはリングバッファへの出し入れだけを行い、
実際の計算は別スレッドが担当します。

| コールバック | 役割 |
|---|---|
| `micInputProc` | マイクから読んで `ringMic` へ入れる |
| `bh16Proc` | BlackHole 16ch から読んで `ringRef`(AEC 用)と `ringRefSpk`(スピーカー用)の両方へ入れる |
| `spkRenderProc` | `ringRefSpk` から取り出して実際のスピーカーへ出す |
| `bh2Proc` | `ringOut` から取り出して BlackHole 2ch へ出す |

### 四つのリングバッファ

`Ring` クラス。ロックなしで使う円環バッファです。それぞれにバックログ上限があり、
超えたら古いものを捨てます。捨てないと遅延が増え続けます。

| バッファ | 上限 | 役割 |
|---|---|---|
| `ringMic` | 200 ms | マイク入力 |
| `ringRef` | 100 ms | AEC 参照 |
| `ringRefSpk` | 100 ms | スピーカー出力 |
| `ringOut` | なし | AEC 結果 |

**`ringRefSpk` と `ringRef` は同じ信号を持ちますが用途が違います。** 前者は利用者
が聞く音なので遅延が短くあるべきで、後者は AEC の整合用なので余裕が要ります。
この二つを同じ値で扱うと片方が壊れます。7 節で扱います。

### ワーカースレッド

`SpeexAecWorker.loop()` が本体です。480 サンプル(10 ms)ずつ処理します。

1. `ringMic` と `ringRef` から 1 フレームずつ取り出す
2. 参照を遅延線(`refDelayBuf`)に通してマイクと時間軸を合わせる
3. Float32 を Int16 に変換する(speexdsp が整数しか受け取らない)
4. `speex_echo_cancellation()` でエコーを引く
5. `speex_preprocess_run()` で残留エコーと雑音を抑える
6. Float32 に戻して `ringOut` へ書く

### 遅延の整合

AEC が働くにはマイク信号と参照信号の時間軸が合っている必要があります。参照が
100 ms 遅れて届けば、AEC は 100 ms ずれた信号を引こうとし、何も消えません。

`calibrateDelay()` がこれを自動で合わせます。マイクと参照を 1.5 秒ずつ集めて
**相互相関**を計算します。参照を d だけずらしたときマイクと最も似る d が実際の
遅延です。

固定値を与えるより自動補正のほうがはるかに良い、というのが実測結果です。

| refdelay | 抑圧量(2 回) |
|---|---|
| 0 ms | 7.6 / 2.7 |
| 60 ms | 7.3 / 1.2 |
| 90 ms | 0.5 / 3.9 |
| 115 ms(実測した本当の遅延) | 7.5 / 4.5 |
| 140 ms | 0.5 / 1.9 |
| 180 ms | -0.1 / 0.9 |
| **自動** | **11.5 / 10.4** |

本当の遅延である 115 ms を固定で与えても、自動補正より劣ります。通話中に遅延が
動いているためと見られます。

キャリブレーションは**別スレッド**で回ります。本ループを止めるとその間オーディオ
が止まるためです。結果が出たら `pendingRefDelay` に書いておき、本ループがフレーム
境界で拾います。

## 6. 踏んだ罠

### 無音と AEC 成功は測定値が同じ

最も痛かった罠です。二度引っかかりました。

エコーが -59 dB と測れたなら、AEC がうまく消したか、スピーカーが鳴らなかったか
のどちらかです。数字だけでは区別できません。

一度はオーディオユーティリティを強制終了した際にミュート状態が残ってスピーカーが
無音になり、それを AEC の効果と取り違えました。もう一度は再生コマンドが音を出して
いなかったのに、それも成功と読みました。

**対照群が答えです。** AEC を切った状態(`--mode bypass`)を並べて測り、抑圧量が
きっちり 0 かを確認します。0 なら信号が実在したという意味です。検証スクリプトは
そう作ってあります。

### `afplay -d` はデバイス指定ではない

`afplay -d "BlackHole 16ch"` で特定デバイスへ再生しようとしました。`-d` は debug
オプションで、afplay にデバイス選択機能自体がありません。音は静かに既定の出力へ
流れていました。

この誤用で複数の測定が無効になりました。今は中継の `--farfile` オプションで
BlackHole へ直接書きます。

### 16 チャンネル平均が 18 dB を食った

BlackHole 16ch はチャンネルを 16 個報告しますが、通話アプリは先頭 2 個しか使い
ません。モノラルにまとめるとき 16 で割ると振幅が 8 分の 1 になります。ちょうど
-18 dB です。

症状は「相手の声が小さい」で、最初はこれを**エコーが消えたと取り違えました。**
スピーカーが静かになればマイクに入るエコーも減るからです。

`monoFromABL()` が無音チャンネルを除いて有効チャンネルだけを平均するよう直しま
した。

### スピーカーバッファに上限がなく声が遅れた

`ringRefSpk` だけバックログ上限がありませんでした。実通話で遅延が 352 ms から
523 ms を経て 651 ms まで単調に増えました。「声が遅い」という報告になりました。

上限をかけて 89 ms 固定にしました。

### 参照がマイクより 320 ms 遅れて届いた

`ringRef` にも上限はありましたが、判定式が `min(ref, mic) > 200ms` でした。マイク
は常に即座に空くので `min` は 0 に近く、参照に 320 ms 溜まっても一つも捨てられま
せんでした。

参照単独の上限を別にかけました。

### キャリブレーションが実通話では毎回失敗した

元の実装は開始後 3 秒以内に一度だけ試し、信号が弱ければ諦めるものでした。ベンチ
はテスト音声が即座に鳴るので成功しますが、実通話は電話をかけた瞬間は相手が話して
いないので**毎回失敗しました。**

これが「ベンチでは通るのに実通話では通らない」現象の主因でした。

信号が十分になるまで最大 90 秒リトライするよう直しました。実通話のログで 17 秒に
補正が入るのを確認しています。

```
정합 캘리브레이션: lag=240 samples (5.0 ms) corr=0.193 (17s 후)
refdelay 적용: 240 samples (5.0 ms) — AEC 상태 리셋
```

## 7. 遅延と抑圧量はトレードオフ

「少し遅い」という声を受けてバッファを削ったところ、三回続けて悪化しました。

| refMaxBacklog / spkMaxBacklog | 抑圧量 |
|---|---|
| 100 ms / 100 ms | 8-14 dB |
| 50 ms / 40 ms | 1-3 |
| 100 ms / 40 ms | 3-7 |

**`spkMaxBacklog` で捨てるサンプルは、そのままスピーカーへ出る信号であり、それが
マイクへ戻るエコーの原本です。** 捨てると AEC が学習した経路と合わなくなります。
体感遅延だけをいじる値ではありませんでした。

体感遅延を減らすなら `ringOut`(AEC 結果が通話アプリへ出る道)を触ります。こちら
はキャンセル経路の外です。

## 8. 失敗した改善の試み

実通話で「話が長くなるとエコーを感じる」という報告を受け、原因を二つに絞りました。

1. 参照バッファの遅延が通話中に動く(68 → 25 → 36 ms を観測)
2. 参照が無音の区間(実通話の 60-86%)にも AEC を回し、フィルタが「参照なし =
   エコーなし」を学習する

三つとも直してみて、三つとも抑圧量が落ちました。

| 試み | 抑圧量 |
|---|---|
| 手を付ける前 | 5.6-9.4 dB |
| 遅延線の整合 + フィルタリセット | 3.4-5.6 |
| リセットだけ除去 | 1.8-5.8 |
| エコーの尾を待ってから無音ゲート | 0.8-4.8 |

すべて元に戻しました。

### ベンチが実通話を再現していなかった

三度失敗した後で測定条件を疑いました。35 秒の実音声で測り直すと 47 dB が出ました。
実通話の 8-14 dB とかけ離れています。

**ベンチにダブルトークがありませんでした。** 従来の測定は参照(相手の声)だけが
鳴り、利用者は話さない条件です。実通話は二人が同時に話し、そのとき適応フィルタが
利用者の声をエコーと取り違えてずれます。

`pm_doubletalk.sh` がこれを再現します。相手の声は中継の `--farfile` でスピーカーへ
出して参照に入れ、利用者の声は既定出力を別のスピーカーに切り替えて `say` で鳴らし
ます。後者は参照に存在しないので AEC からは見えない信号です。マイクが両方を拾って
ダブルトークになります。

これで残留エコー抑圧の強さを測りました。

| esupActive | 相手のみ | ダブルトーク |
|---|---|---|
| -15(既定) | -48.7 | -48.9 |
| -30 | -51.3 | -48.4 |

差がありません。このパラメータは原因ではありません。-45 と -60 は測定前に中断
しました。

> **後から訂正したこと。** 上の 47 dB は実通話の 8-14 dB と比較できる値では
> ありません。前者は参照対出力で計算していて空気経路の減衰まで含み、後者はマイク
> 対出力です。基準を揃えて並べ直すとベンチ、ダブルトーク、実通話の三つが近い範囲
> に収まり、ダブルトークがボトルネックだという結論は**成り立ちません。** 本当の
> ボトルネックはまだ特定できていません。

---

## 9. 残っている問題

**抑圧量が頭打ちだが原因が分からない。** 測定基準を正すまではダブルトークが有力な
仮説でしたが、基準を揃えると三条件が同じ範囲に入ります。何が抑圧量を 8-14 dB に
留めているのかは、まだ特定できていません。

speexdsp を WebRTC AEC3 に置き換えるのが次の手です。Chrome が使っているエンジンで、
ダブルトーク処理が優れていると言われています。ただし C++ ライブラリを持ってきて
繋ぐ作業なので作り直しの規模であり、**ボトルネックを特定する前に始めるものでは
ありません。**

**通話検知ができない。** `callwatch.swift` が `avconferenced` のオーディオデバイス
占有を 1 秒ごとに確認して通話開始を捉えようとしましたが、通話中でも何も検知でき
ませんでした。今は中継を常時動かすことで代替しています。

## 10. 現在の運用

launchd エージェント(`com.neocode24.aecrelay`)として登録し、ログイン時に自動起動、
落ちたら復帰させています。ターミナルを開く必要はありません。

FaceTime のビデオメニューでマイクを BlackHole 2ch、出力を BlackHole 16ch に一度
指定しておけば電話アプリも従います。二つのアプリが `avconferenced` バックエンドを
共有しているためです。

**システムの既定出力は元のデバイスのままです。** 音楽や動画の音は中継を通りません。
BlackHole を使うのは FaceTime と電話アプリだけです。

中継を止める用事ができたら、FaceTime も実際のマイクとスピーカーに戻します。
BlackHole のまま中継がないと相手の声が聞こえません。

管理コマンドは README を参照してください。
