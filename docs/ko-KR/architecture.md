# 구조와 배경

**언어** · [English](../en/architecture.md) · 한국어 · [日本語](../ja-JP/architecture.md) · [← README](README.md)

`speexrelay`가 무엇을 하는 프로그램이고 왜 이런 모양이 됐는지 적는다.
나중에 다시 손댈 때 같은 자리를 다시 파지 않으려고 남긴다.

작업일 2026-09-12.

---

## 1. 에코는 왜 생기나

통화 중에 상대 목소리가 스피커로 나온다. 그 소리가 공기를 타고 내 마이크로
다시 들어간다. 마이크에 들어간 것은 통화 회선을 타고 상대에게 되돌아간다.
상대는 자기가 방금 한 말을 몇백 밀리초 뒤에 다시 듣는다. 이것이 에코다.

에코를 듣는 쪽은 상대이지 내가 아니다. 그래서 내 귀로는 문제를 확인할 수
없고, 통화할 때마다 상대에게 물어봐야 한다. 오늘 작업이 오래 걸린 이유 중
하나가 이것이다.

해결 방향은 둘이다.

**스피커 소리가 마이크에 안 들어가게 한다.** 헤드셋을 쓰면 끝난다. 다만
스피커로 통화하고 싶으면 못 쓴다.

**마이크에 들어간 에코를 지운다.** 이것이 AEC(Acoustic Echo Cancellation,
음향 반향 제거)다. 스피커로 내보낸 신호를 알고 있으니, 마이크 신호에서 그것을
빼면 된다는 발상이다. 이 저장소가 만든 것이 여기 해당한다.

### 왜 단순 뺄셈이 아닌가

스피커로 내보낸 신호와 마이크로 되돌아온 신호는 같지 않다. 방을 한 번
돌아오면서 이런 변형을 겪는다.

- **지연.** 소리가 스피커에서 마이크까지 가는 시간, 그리고 오디오 장치가
  버퍼에 담아두는 시간이 더해진다. 여기서 실측한 값은 115ms였다.
- **감쇠와 왜곡.** 스피커와 마이크의 주파수 특성이 다르고, 벽에 반사된 소리가
  겹친다.
- **잔향.** 한 번의 소리가 여러 경로로 반사되어 시간에 걸쳐 도착한다.

그래서 AEC는 "스피커 신호가 마이크에 도달할 때 어떤 모양이 되는가"를 실시간
으로 추정한다. 이 추정을 **적응 필터**라고 부르고, 추정한 것을 마이크 신호에서
빼는 것이 에코 제거다. 통화가 진행되는 동안 계속 학습한다.

## 2. macOS는 이걸 왜 안 해주나

FaceTime과 전화 앱은 `avconferenced`라는 시스템 데몬이 오디오를 처리한다.
이 데몬 안에 AEC가 있기는 한데, 이 환경에서는 동작하지 않았다.

애플이 개발자에게 제공하는 AEC는 `AUVoiceProcessingIO`(줄여서 VPIO)라는
오디오 유닛이다. 세 가지 방법으로 시도했고 셋 다 막혔다.

| 시도 | 결과 |
|---|---|
| VPIO에 마이크만 물리고 시스템 출력을 참조로 쓰기 | 참조 콜백이 한 번도 호출되지 않음 (`cb=0`) |
| VPIO 출력으로 상대 목소리를 렌더하고 그 신호를 참조로 쓰기 | 마이크에서 가상 장치로 가는 배관이 죽음 |
| Aggregate Device로 마이크와 스피커를 한 유닛에 묶기 | `-10851` 오류로 거부 |

**첫 번째가 막힌 이유가 핵심이다.** VPIO의 AEC는 **자기 자신의 출력 버스로
렌더된 신호만** 참조로 쓴다. `avconferenced`가 스피커로 직접 보낸 소리는 VPIO가
모르므로 참조가 없다. 참조 없는 AEC는 아무것도 못 지운다.

세 번째도 같은 제약에서 나온다. `kAudioOutputUnitProperty_CurrentDevice`는
장치를 하나만 받는다. 입력은 마이크, 출력은 모니터로 서로 다르게 물리려면
Aggregate Device로 묶어야 하는데 VPIO가 그것을 거부한다.

또 하나 시도한 것이 Core Audio의 **process tap**이다. 다른 프로세스의 오디오
출력을 가로채는 API인데, tap 생성까지는 성공했으나 콜백이 한 번도 오지
않았다. 서명 없는 CLI 바이너리라 시스템 오디오 캡처 권한(TCC)이 없어서로
보인다.

**결론은 이랬다.** 애플 AEC는 참조 신호를 못 받으니 쓸 수 없고, 시스템 오디오를
직접 가로채는 것도 권한 때문에 막힌다. 참조 신호를 다른 방법으로 확보하고,
AEC 엔진도 직접 붙여야 한다.

## 3. BlackHole이 필요한 이유

참조 신호를 얻으려면 상대 목소리가 스피커로 가기 **전에** 그 신호를 봐야 한다.
`avconferenced`가 스피커로 직접 보내면 우리는 볼 방법이 없다.

그래서 통화 앱의 출력을 **가상 오디오 장치**로 돌린다. 가상 장치는 출력으로
쓰면 소리를 삼키고, 입력으로 쓰면 방금 삼킨 그 소리를 그대로 내놓는다. 통화
앱이 그쪽으로 소리를 보내면 우리 프로그램이 그것을 읽을 수 있다.

`BlackHole`이 그 가상 장치다. 오픈소스이고 brew로 설치된다.

두 벌이 필요하다. 하나는 상대 목소리를 받는 통로(통화 앱 → 우리), 다른 하나는
처리한 마이크 신호를 보내는 통로(우리 → 통화 앱)다. 방향이 반대라 같은 장치를
쓸 수 없다.

brew에는 `blackhole-2ch`, `blackhole-16ch`, `blackhole-64ch`가 따로 있고 2ch를
두 벌 설치하는 방법이 없다. 그래서 2ch와 16ch를 하나씩 설치했다. **16채널이
필요해서 고른 것이 아니라 서로 다른 장치가 필요해서 골랐다.**

이 선택이 나중에 문제를 하나 만들었다. 6절에서 다룬다.

## 4. 신호 흐름

장치 네 개가 관여한다.

```
                    상대 목소리
                        |
              [FaceTime / 전화 앱]
                    |        ^
         출력       |        |      마이크
                    v        |
          BlackHole 16ch   BlackHole 2ch
                    |        ^
                    |        |
        +-----------+--------+-----------+
        |        speexrelay              |
        |                                |
        |   참조 신호 ---> [speexdsp AEC] |
        |       |              ^         |
        |       |              |         |
        |       v              |         |
        |    [스피커]     내 마이크 신호 |
        +-----------|----------|---------+
                    |          |
                    v          |
                 스피커          마이크
              (실제 출력 장치)  (실제 입력 장치)
                    |          ^
                    +---에코---+
                     (공기를 타고)
```

경로를 하나씩 따라가면 이렇다.

**상대 목소리가 오는 길.** FaceTime이 BlackHole 16ch로 출력한다. `speexrelay`가
그것을 읽어 두 곳으로 보낸다. 하나는 실제 스피커(사용자가 듣는다), 다른 하나는
AEC의 참조 입력이다. 같은 신호를 둘로 나누는 것이 이 구조의 핵심이다.

**내 목소리가 가는 길.** 마이크에서 읽은 신호를 AEC에 넣는다. AEC가
참조를 이용해 에코 성분을 빼고, 결과를 BlackHole 2ch로 쓴다. FaceTime은 이것을
마이크 입력으로 받는다.

**에코가 생기는 길.** 스피커에서 나온 소리가 공기를 타고 마이크로 들어간다.
이것이 지워야 할 대상이고, 참조 신호와 같은 원본에서 나왔으므로 지울 수 있다.

`speexrelay`가 꺼져 있으면 BlackHole 16ch에 들어온 소리를 아무도 꺼내지 않는다.
상대 목소리가 그 자리에서 사라진다. **릴레이를 먼저 켜고 통화해야 하는 이유가
이것이다.**

## 5. 코드 구조

`speexrelay.swift` 한 파일이다. 986줄.

### 오디오 콜백 넷

CoreAudio는 실시간 스레드에서 콜백을 부른다. 이 안에서 오래 걸리는 일을 하면
소리가 끊긴다. 그래서 콜백은 링버퍼에 넣고 빼기만 하고, 실제 계산은 별도
스레드가 한다.

| 콜백 | 하는 일 |
|---|---|
| `micInputProc` | 마이크에서 읽어 `ringMic`에 넣는다 |
| `bh16Proc` | BlackHole 16ch에서 읽어 `ringRef`(AEC용)와 `ringRefSpk`(스피커용) 둘에 넣는다 |
| `spkRenderProc` | `ringRefSpk`에서 꺼내 실제 스피커로 내보낸다 |
| `bh2Proc` | `ringOut`에서 꺼내 BlackHole 2ch로 내보낸다 |

### 링버퍼 넷

`Ring` 클래스. 락 없이 쓰는 원형 버퍼다. 각각 백로그 상한이 있고, 넘으면 오래된
것을 버린다. 안 버리면 지연이 계속 늘어난다.

| 버퍼 | 상한 | 역할 |
|---|---|---|
| `ringMic` | 200ms | 마이크 입력 |
| `ringRef` | 100ms | AEC 참조 |
| `ringRefSpk` | 100ms | 스피커 출력 |
| `ringOut` | 없음 | AEC 결과 |

**`ringRefSpk`와 `ringRef`는 같은 신호를 담지만 용도가 다르다.** 전자는
사용자가 듣는 소리라 지연이 짧아야 하고, 후자는 AEC 정합용이라 넉넉해야 한다.
이 둘을 같은 값으로 다루면 한쪽이 망가진다. 7절에서 다룬다.

### 워커 스레드

`SpeexAecWorker.loop()`가 본체다. 480샘플(10ms)씩 처리한다.

1. `ringMic`과 `ringRef`에서 한 프레임씩 꺼낸다
2. 참조를 지연선(`refDelayBuf`)에 통과시켜 마이크와 시간축을 맞춘다
3. Float32를 Int16으로 바꾼다 (speexdsp가 정수만 받는다)
4. `speex_echo_cancellation()`으로 에코를 뺀다
5. `speex_preprocess_run()`으로 잔여 에코와 잡음을 누른다
6. Float32로 되돌려 `ringOut`에 쓴다

### 지연 정합

AEC가 동작하려면 마이크 신호와 참조 신호의 시간축이 맞아야 한다. 참조가 100ms
늦게 도착하면 AEC는 100ms 어긋난 신호를 빼려 하고, 그러면 아무것도 안 지워진다.

`calibrateDelay()`가 이것을 자동으로 맞춘다. 마이크와 참조를 1.5초씩 모아
**상호상관**을 계산한다. 참조를 d만큼 밀었을 때 마이크와 가장 비슷해지는 d를
찾으면 그것이 실제 지연이다.

고정값을 주는 것보다 자동 보정이 훨씬 낫다. 실측 결과다.

| refdelay | 억제량 (2회) |
|---|---|
| 0ms | 7.6 / 2.7 |
| 60ms | 7.3 / 1.2 |
| 90ms | 0.5 / 3.9 |
| 115ms (측정된 실제 지연) | 7.5 / 4.5 |
| 140ms | 0.5 / 1.9 |
| 180ms | -0.1 / 0.9 |
| **자동** | **11.5 / 10.4** |

실제 지연인 115ms를 고정으로 줘도 자동 보정보다 나쁘다. 지연이 통화 중에
변하기 때문으로 보인다.

캘리브레이션은 **별도 스레드**에서 돈다. 본 루프를 막으면 그동안 오디오가
멈추기 때문이다. 결과가 나오면 `pendingRefDelay`에 써두고 본 루프가 프레임
경계에서 집어간다.

## 6. 오늘 밟은 함정들

### 무음과 AEC 성공은 측정값이 같다

가장 많이 당한 함정이다. 두 번 속았다.

에코가 -59 dB로 측정되면 AEC가 잘 지웠거나, 스피커가 아예 안 울렸거나 둘 중
하나다. 숫자만 보면 구분이 안 된다.

한 번은 오디오 유틸리티를 강제 종료하면서 음소거 상태가 남아 스피커가 무음이
됐고, 그것을 AEC 효과로 착각했다. 또 한 번은 재생 명령이 소리를 안 냈는데
그것도 성공으로 읽었다.

**대조군이 답이다.** AEC를 끈 상태(`--mode bypass`)를 같이 재서 억제량이
정확히 0인지 확인한다. 0이면 신호가 실제로 있었다는 뜻이다. 지금 검증
스크립트가 그렇게 만들어져 있다.

### `afplay -d`는 장치 옵션이 아니다

`afplay -d "BlackHole 16ch"`로 특정 장치에 재생하려 했다. `-d`는 debug 옵션이고
afplay에는 출력 장치를 고르는 기능 자체가 없다. 소리는 조용히 기본 출력으로
나갔다.

이 오용으로 여러 측정이 무효가 됐다. 지금은 릴레이의 `--farfile` 옵션으로
BlackHole에 직접 쓴다.

### 16채널 평균이 -18 dB를 먹었다

BlackHole 16ch는 채널 16개를 보고하는데 통화 앱은 앞 2개에만 쓴다. 모노로
합칠 때 16으로 나누면 진폭이 8분의 1이 된다. 정확히 -18 dB다.

증상은 "상대 목소리가 작게 들린다"였고, 처음에는 이것을 **에코가 사라진 것으로
착각했다.** 스피커가 조용해지니 마이크에 들어가는 에코도 줄었던 것이다.

`monoFromABL()`이 무음 채널을 빼고 활성 채널만 평균하도록 고쳤다.

### 스피커 버퍼에 상한이 없어 목소리가 느려졌다

`ringRefSpk`만 백로그 상한이 없었다. 실통화에서 지연이 352ms에서 523ms를 거쳐
651ms까지 단조 증가했다. 사용자 표현으로 "목소리가 느리다"였다.

상한을 걸어 89ms 고정으로 만들었다.

### 참조가 마이크보다 320ms 늦게 도착했다

`ringRef`에도 상한이 있었지만 판정식이 `min(ref, mic) > 200ms`였다. 마이크는
늘 즉시 비워지므로 `min`이 0에 가깝고, 참조에 320ms가 쌓여도 아무것도 안
버려졌다.

참조 단독 상한을 따로 걸었다.

### 캘리브레이션이 실통화에서 항상 실패했다

원래 구현은 시작 후 3초 안에 한 번만 시도하고 신호가 약하면 포기했다.
측정 모드는 테스트 음성이 즉시 나오니 성공했는데, 실통화는 전화를 거는 순간
상대가 말을 안 하니 **매번 실패했다.**

이것이 "측정에서는 되는데 실통화에서는 안 되는" 현상의 주범이었다.

신호가 충분해질 때까지 최대 90초 재시도하도록 고쳤다. 실통화 로그에서 17초에
보정이 붙는 것을 확인했다.

```
정합 캘리브레이션: lag=240 samples (5.0 ms) corr=0.193 (17s 후)
refdelay 적용: 240 samples (5.0 ms) — AEC 상태 리셋
```

## 7. 지연과 억제량은 맞바꾸는 관계다

"조금 느리다"는 말에 버퍼를 줄였다가 세 번 연속 나빠졌다.

| refMaxBacklog / spkMaxBacklog | 억제량 |
|---|---|
| 100ms / 100ms | 8 - 14 dB |
| 50ms / 40ms | 1 - 3 |
| 100ms / 40ms | 3 - 7 |

**`spkMaxBacklog`에서 버리는 샘플이 곧 스피커로 나가는 신호이고, 그것이
마이크로 되돌아오는 에코의 원본이다.** 버리면 AEC가 학습한 경로가 어긋난다.
체감 지연만 건드리는 값이 아니었다.

체감 지연을 줄이려면 `ringOut`(AEC 결과가 통화 앱으로 나가는 길)을 건드려야
한다. 이쪽은 AEC와 무관하다.

## 8. 실패한 개선 시도

실통화에서 "말이 길어지면 에코가 느껴진다"는 보고를 받고 원인을 둘로 좁혔다.

1. 참조 버퍼 지연이 통화 중 움직인다 (68 -> 25 -> 36ms 관측)
2. 참조가 무음인 구간(실통화의 60-86%)에도 AEC를 돌려 필터가
   "참조 없음 = 에코 없음"을 학습한다

셋 다 고쳐봤고 셋 다 억제량이 떨어졌다.

| 시도 | 억제량 |
|---|---|
| 손대기 전 | 5.6 - 9.4 dB |
| 지연선 정합 + 필터 리셋 | 3.4 - 5.6 |
| 리셋만 제거 | 1.8 - 5.8 |
| 에코 꼬리 대기 후 무음 게이팅 | 0.8 - 4.8 |

전부 되돌렸다.

### 측정이 실통화를 재현하지 못했다

세 번 실패한 뒤에 측정 조건을 의심했다. 35초짜리 실제 음성으로 재보니 47 dB가
나왔다. 실통화의 8-14 dB와 너무 다르다.

**측정에 더블토크가 없었다.** 기존 측정은 참조(상대 목소리)만 울리고 사용자는
말하지 않는 조건이다. 실통화는 둘이 동시에 말하고, 그때 적응 필터가 사용자
목소리를 에코로 오인해 어긋난다.

`pm_doubletalk.sh`가 이것을 재현한다. 상대 목소리는 릴레이의 `--farfile`로
스피커로 내보내 참조에 들어가게 하고, 사용자 목소리는 기본 출력을 다른
스피커로 돌려 `say`로 낸다. 후자는 참조에 없으므로 AEC가 모르는 신호다.
마이크가 둘 다 주워담아 더블토크가 된다.

이걸로 잔여 에코 억제기 세기를 재봤다.

| esupActive | 상대만 | 더블토크 |
|---|---|---|
| -15 (기본) | -48.7 | -48.9 |
| -30 | -51.3 | -48.4 |

차이가 없다. 이 파라미터는 원인이 아니다. -45와 -60은 측정 전에 중단했다.

> **나중에 바로잡은 것.** 위의 47 dB는 실통화의 8-14 dB와 비교할 수 있는 값이
> 아니다. 전자는 참조 대비 출력으로 계산해 공기 경로의 감쇠까지 포함하고,
> 후자는 마이크 대비 출력이다. 기준을 맞춰 다시 놓으면 시험대, 더블토크,
> 실통화 셋이 비슷한 범위에 들어오고 더블토크가 병목이라는 결론은 **서지
> 않는다.** 진짜 병목은 아직 찾지 못했다.

## 9. 남은 문제

**억제량이 제한되는데 원인을 모른다.** 측정 기준을 바로잡기 전까지는 더블토크가
유력한 가설이었으나, 기준을 맞춰 보니 세 조건이 같은 범위에 들어온다. 무엇이
억제량을 8-14 dB에 묶어 두는지는 아직 특정하지 못했다.

speexdsp를 WebRTC AEC3로 바꾸는 것이 다음 수단이다. 크롬이 쓰는 엔진이고
더블토크 처리가 낫다고 알려져 있다. 다만 C++ 라이브러리를 가져와 붙이는 일이라
새로 만드는 규모이고, **병목을 특정하기 전에는 시작할 일이 아니다.**

**통화 감지가 안 된다.** `callwatch.swift`가 `avconferenced`의 오디오 장치 점유를
1초마다 확인해 통화 시작을 잡으려 했으나 통화 중에도 아무것도 감지하지 못했다.
지금은 릴레이를 상시 켜두는 것으로 대체했다. 코드는 참고용으로 남겼다.

## 10. 현재 운영 방식

launchd 에이전트(`com.neocode24.aecrelay`)로 등록해 로그인 시 자동 실행하고,
죽으면 되살린다. 터미널을 열 필요가 없다.

FaceTime 비디오 메뉴에서 마이크를 BlackHole 2ch, 출력을 BlackHole 16ch로 한 번
지정해두면 전화 앱도 따라간다. 두 앱이 `avconferenced` 백엔드를 공유하기
때문이다.

**시스템 기본 출력은 원래 장치 그대로다.** 음악이나 영상 소리는 릴레이를 안 거친다.
BlackHole을 쓰는 것은 FaceTime과 전화 앱뿐이다.

릴레이를 정지할 일이 생기면 FaceTime도 실제 마이크와 스피커로 되돌려야 한다. BlackHole로
둔 채 릴레이가 없으면 상대 목소리가 안 들린다.

관리 명령은 README를 참조한다.
